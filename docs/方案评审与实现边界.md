# 方案评审与首轮实现边界

## 结论

Flutter + 纯像素 C++ 内核 + 窄 C ABI 的方向成立，没有必须阻塞首轮编码的架构问题。但原方案涉及四端工具链与整套原生依赖，不能把一个 Flutter 页面工程等同于四端落地。本轮以 macOS 编辑流程的源代码、共享内核及测试/构建入口为交付；真实设备、真实相机样张和其他端依赖交叉编译仍须独立验收。

## 实现时补充的决策

### 1. 不混淆 16bit 与线性空间

16bit 只是表示精度，不能自动保证 JPEG 和 RAW 在相同空间。内核明确采用线性 sRGB RGBA16：普通图片先去除显示传递函数或由 ICC 转换，RAW 则明确要求 LibRaw 线性 sRGB 输出。LUT 明确在 SDR sRGB 显示域应用。

8bit 上采样不会产生原始文件中不存在的细节；它只能减少后续多步处理重复量化的误差。首版调色仍会裁剪到 SDR 范围，不承诺保留 HDR/场景线性超白数据。

### 2. ABI 不能只有业务函数，还必须有所有权

图像和 LUT 使用不可变句柄；创建、检查信息、预览拷贝、释放、错误码和 ABI 版本属于接口的一部分。所有像素内存由同一个动态库分配与释放。异常在 C++ 边界内截获，错误文本按线程隔离，不暴露 C++ 标准库类型给 Dart。

### 3. 非破坏编辑与预览调度留在 Dart

历史只记录参数配方；一次滑杆拖动生成一个历史节点。常驻预览工作线程缓存小图，主线程合并请求，只展示最新版本。原图导出在另一个工作线程重新解码，不拿预览图放大。内核不维护编辑历史或业务全局状态。

### 4. EXIF 不是无条件原样复制

图像方向在解码时归一化，导出方向必须为 1，尺寸必须更新。旧缩略图、MakerNote、原始 ICC 不能盲目复制，GPS 默认不保留。

Exiv2 的许可证影响整体分发策略。首版没有引入它，而是采用必要字段白名单；这是一项明确的 MVP 收敛，不是已经实现了全部元数据兼容。发布前仍须确定 LibRaw 等依赖的许可选择并履约。

### 5. 所有编码器都有实际可用性边界

HEIF 容器库存在不等于具体编码器存在；用户选择 HEIF 导出后，缺少编码器应返回明确错误，不能伪装成功。PQ/HLG HDR、CMYK JPEG 和动画 WebP 暂不支持。RAW 的支持以 LibRaw 判定和真实机型样张验证为准，不靠扩展名承诺。

### 6. 鸿蒙不是一个未经验证就算完成的编译参数

纯 C++ 核心可以复用，但文件/相册插件、NAPI、NDK/SDK 版本、依赖构建和显存传递仍是平台工作。当前没有将这些未完成项包装成“支持鸿蒙”。同理，Android/iOS 的原生依赖不能复用 macOS Homebrew 二进制。

4. 移动端最大输入像素、内存预算、低内存降级与分块导出策略。
5. 应用名称“光屿”只是开发界面暂用名，尚未做商标和商店名称核验。
